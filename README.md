# robops — Roblox DevOps on the command line

`robops` is a Python CLI that **overwrites the content of your Roblox places** (and, if you want, the data in your DataStores) from your Git repository, through the official **Open Cloud** API. It is designed to run in **GitHub Actions**: a push to `develop` updates staging, and the live game is only published when you click *Run workflow* (see [Configuring GitHub](#configuring-github)).

```
push main ──► Rojo build ──► checks ──► publish places ──────► metadata
                                           │                         │
                                           └──► DataStores (opt-in) ─┴──► server restart
```

## What it does

| Step | Detail | API key permission |
|---|---|---|
| Build | runs `rojo build` (or any other command) | — |
| Checks | files present, `.rbxl`/`.rbxlx`, valid data JSON — **before** any network call | — |
| Publishing | each place is overwritten by its file (new `Published` or `Saved` version) | `universe-places:write` |
| Metadata | name, description, players per server | `universe.place:write` |
| DataStores | backup snapshot, then overwrite the keys from a JSON | `universe-datastores.objects:update` + `:create` + `universe-datastores.control:snapshot` |
| Restart | switches the servers to the new version | `universe:write` |
| Players (`robops player`) | backup, restore, edit ProfileStore / DataService profiles | `universe-datastores.objects:list` + `:read` + `:update` (+ `:create`, `:delete`) |

Other points:
- automatic retries (429 / 5xx) with exponential backoff, honouring `Retry-After`;
- error messages that include the probable cause (expired key, IP not allowed, missing permission…);
- in CI: grouped logs, `::error::` annotations, deployment summary in the *Summary* tab, published versions exposed as *outputs*;
- `--dry-run`: build + checks without ever contacting Roblox (used on pull requests);
- if a deployment stops halfway, the *Summary* tab still says which places are already live (`failed` and `versions` outputs);
- a typo in `robops.toml` (`restart_server`, `versoin_type`…) is an error with a suggestion, never silently ignored.

## Windows version (.exe) with installer and automatic update

On your PC you can use `robops.exe` without installing Python. The executables are compiled by GitHub Actions on a Windows machine and published in the tool repository's *Releases*.

### Setup (one time only)

1. Create a repository named `robops` on GitHub (private or public) and push the content of this folder to it, at the root:

   ```bash
   cd robops
   git init
   git add .
   git commit -m "robops 1.3.0"
   git branch -M main
   git remote add origin https://github.com/YOUR-ACCOUNT/robops.git
   git push -u origin main
   ```

2. Start the build: **Actions** tab of the `robops` repository → **Release** (left column) → **Run workflow** → branch `main` → **Run workflow**.

   In about 8 minutes, the workflow runs the tests, compiles robops (as a folder, zipped in `robops-windows.zip`, and as a single `robops.exe`) and `robops-setup.exe` on a Windows machine, tests them (including a real install, an update while robops is running and an uninstall), computes their SHA-256 checksums, attests their build provenance and creates the release `v1.3.0` (the version in `src/robops/__init__.py`). The repository name (`StarLightFr51/robops`, `DEFAULT_REPOSITORY` in `src/robops/__init__.py`) is burned into the executables, and also used as a fallback if it is missing: nothing to configure.

3. The files appear in the **Releases** section, on the right of the repository's home page.

If you prefer git, pushing the tag `v1.3.0` (`git tag v1.3.0 && git push origin v1.3.0`) triggers the same thing.

### Installing on a PC

Download `robops-setup.exe` from the *Releases* page and double-click it. The installer:

- queries the repository and fetches the latest version (`robops-windows.zip`);
- verifies its SHA-256 checksum before installing it;
- installs it in `%LOCALAPPDATA%\Programs\robops` (no administrator rights): `robops.exe` and the `_internal` folder of its libraries. robops starts in about 0.3 s this way, against 1.2 s or more for a single .exe, which unpacks its libraries into a temporary folder at every launch;
- adds that folder to your Windows account's **PATH**, so `robops` works in any terminal;
- registers it in **Apps & features** so it can be uninstalled.

Then open a **new** terminal and type `robops --version`. Running the installer again later updates the tool (`--force` to reinstall the same version).

> The .exe files are not digitally signed: on first launch, Windows SmartScreen shows "Windows protected your PC". Click **More info** then **Run anyway**. Some antivirus programs also wrongly flag programs compiled with PyInstaller. Removing these warnings requires a code-signing certificate (paid).
>
> To check that a downloaded .exe really was built by this repository's release workflow (public repository): `gh attestation verify robops-setup.exe --repo StarLightFr51/robops`.

### Updates

- At most once a day, after a command, `robops.exe` checks whether a newer release exists and **tells you** (one line on stderr). Nothing is downloaded or replaced without you.
- `robops self-update` installs it (checksum verified, the new version is used from the next launch); `robops self-update --check` only tells you whether there is one. It works even while robops runs elsewhere (dashboard, Claude Desktop): files in use are renamed `*.old` and deleted at a later launch.
- **From robops 1.7 or older** (a single `robops.exe`): the first `robops self-update` installs 1.8 as a single file, a second `robops self-update` moves it to the folder. Or run `robops-setup.exe` again: it installs the folder straight away.
- Prefer silent installation, as in versions before 1.3? Set the user environment variable `ROBOPS_AUTO_UPDATE=1`. Keep in mind that the checksum comes from the same release: it detects a corrupted download, not a compromised GitHub account.
- A failed check (no network…) shows a warning but never makes your command fail.
- The check is **disabled in CI** (`CI` / `GITHUB_ACTIONS` variables) and with `ROBOPS_NO_UPDATE=1`. With a pip install it does not exist: update with pip.

### Publishing a new version

Bump `__version__` in `src/robops/__init__.py` (for example `1.3.1`), add a line to `CHANGELOG.md`, commit and push, then run **Actions → Release → Run workflow** again. If that version is already published, the workflow stops and asks you to bump the number. Installed PCs are told within 24 h and update with `robops self-update`.

### Private repository

GitHub calls then need a token. Create a *fine-grained token* with only **Contents: Read** on the robops repository, then store it in a Windows user environment variable named `ROBOPS_GITHUB_TOKEN`. The installer, the daily check and `robops self-update` all use it.

### Uninstalling

*Settings → Apps → robops → Uninstall*, or `robops-setup.exe --uninstall` (add `--dir <folder>` if you installed it elsewhere). robops' own files (`robops.exe`, `_internal`, the installer), the PATH entry and the registry entry are removed; the folder itself is only deleted if nothing else is left in it.

### Compiling and installing on your PC, without GitHub

On a Windows PC with Python 3.11+ (installed from python.org, *Add python.exe to PATH* checked), open a terminal in the `robops` folder and run:

```powershell
python exe\build.py --install
```

The script installs PyInstaller if it is missing, compiles robops (2 to 4 minutes), copies `robops.exe` and its `_internal` folder to `%LOCALAPPDATA%\Programs\robops` and adds that folder to your PATH. Then open a **new** terminal: `robops --version`.

To update, run the same command again after pulling the new code. The executables install and update themselves from the GitHub releases of `StarLightFr51/robops` (`DEFAULT_REPOSITORY` in `src/robops/__init__.py`); pass `--repo owner/name` to burn in another repository, or set `ROBOPS_REPO` at run time. Without `--install`, the files are simply produced in `dist/`. PyInstaller cannot produce a Windows .exe from Linux or macOS.

## Installing in your Roblox project

1. Copy the `robops/` folder into your game repository, under `tools/robops/`.
2. Install it locally (Python 3.11 minimum), then generate the configuration:

   ```bash
   pip install ./tools/robops
   robops init
   ```

   This creates `robops.toml`, `.github/workflows/roblox-deploy.yml` and `rokit.toml` (Rojo 7.7.0) — existing files are not overwritten without `--force`.
3. Replace the `0`s in `robops.toml` with your real IDs, then check:

   ```bash
   robops check                       # configuration only
   ROBLOX_API_KEY=... robops check staging --online   # + key and IDs against Roblox
   ```

> **robops in its own GitHub repository** (recommended if you installed `robops.exe`): no need to copy it into your game. Run `robops init --action-repo your-account/robops`: the workflows are pinned to the tag of your robops version (e.g. `your-account/robops@v1.3.0`), so a later push to robops' `main` never changes what runs with your Roblox key. To update, change the tag. You can also replace the two `uses: ./tools/robops` by hand; avoid `@main`. If the `robops` repository is **private**, allow it once: in the `robops` repository, *Settings → Actions → General → Access → "Accessible from repositories owned by the user …" → Save* (your game repository must be private too).

## Creating the Open Cloud API key

Creator Dashboard → **Credentials** → *Create API Key*:

- **Access permissions**: add the relevant experience and the permissions from the table above (at minimum `universe-places` → *Write*).
- **Security → Accepted IP addresses**: GitHub Actions runners change IP on every run, so you must allow `0.0.0.0/0`. This is the #1 cause of **401** errors in CI.
- Set an **expiration date** and ideally use **one key per environment** (staging / production).

## Configuring GitHub

In your game repository: *Settings → Secrets and variables → Actions → Secrets tab → New repository secret*, name **`ROBLOX_API_KEY`**, value = your Roblox key. That's it. You can add a second secret `ROBLOX_API_KEY_PRODUCTION` to use a different key on the live game.

The generated workflow works with a **private** repository and a **free** GitHub account:

| Event | Action |
|---|---|
| Pull request | build + checks (`--dry-run`), nothing is published |
| Push to `main` | build + checks, nothing is published |
| Push to `develop` | automatic publish to the **test** game (`staging`) |
| *Run workflow* button | publish to the **live game** (or staging), with the options of your choice |

The live game therefore **never updates on its own**: you approve by clicking.

**Publishing to the live game:**

1. Push your code to `main` and wait for the green check ✔ in the *Actions* tab (the build works).
2. *Actions* tab → *Roblox Deploy* in the left column → *Run workflow* button on the right.
3. *Use workflow from*: `main`; *Where to publish*: `production` → *Run workflow*.

A minute or two later, the game is up to date. Only people with write access to the repository see this button. Production refuses to run from any branch other than `main`.

Two publishes to the same target never run at the same time, and the published file is kept for 30 days as an artifact.

> **Recommended when your plan allows it** — GitHub *Environments*: create `staging` and `production` (*Settings → Environments*), move `ROBLOX_API_KEY_PRODUCTION` into the `production` environment's secrets, add *Required reviewers*, then uncomment the `environment:` line of the `deploy` job in `roblox-deploy.yml`. The production key is then only readable by a run someone approved. Available on public repositories; on a private one, environment secrets need GitHub Pro/Team and required reviewers GitHub Enterprise. On a free private repository, keep the behaviour described above.

## The `robops.toml` file

```toml
api_key_env = "ROBLOX_API_KEY"

[build]
command = "rojo build default.project.json --output build/game.rbxl"

[environments.production]
universe_id = 1234567890
version_type = "Published"     # or "Saved" (saved, not played)
restart_servers = false

[[environments.production.places]]
name = "main"
place_id = 9876543210
file = "build/game.rbxl"
display_name = "My game"       # optional
server_size = 30               # optional

[[environments.production.datastores]]   # only written with --with-datastores
name = "GameConfig"
file = "data/config.production.json"     # { "key": value, ... }
```

Any value can come from the environment: `universe_id = "${ROBLOX_UNIVERSE_ID}"` or `"${ROBLOX_UNIVERSE_ID:-123}"` with a default value. Variables are only resolved for the environment being deployed. `restart_servers = "${RESTART}"` accepts `true`/`false`, `yes`/`no`, `1`/`0`.

Unknown fields are refused with a suggestion (`'restart_server' (did you mean 'restart_servers'?)`): run `robops check` after editing the file.

## Commands

```bash
# Full deployment of an environment
robops deploy staging
robops deploy production --with-datastores --restart
robops deploy production --place lobby --version-type Saved
robops deploy staging --dry-run

# One-off publish of a file
robops publish build/game.rbxl --env staging
robops publish game.rbxlx --universe-id 123 --place-id 456 --version-type Saved

# Places and servers
robops place get --env production
robops place update --env production --name "My game" --server-size 30
robops servers restart --env production

# DataStores (alias: robops ds)
robops ds stores --env production                  # lists the game's DataStores
robops ds get GameConfig motd --env production
robops ds set GameConfig motd --value '"Double XP this weekend!"' --env production
robops ds list PlayerData --prefix user_ --env staging
robops ds export GameConfig --out backup.json --env production
robops ds import GameConfig data/config.json --env production --dry-run
robops ds delete GameConfig old_key --env staging
robops ds snapshot --env production

# Everything above, in a web page
robops dashboard

# Claude saves its player simulations for the dashboard (robops MCP server)
robops mcp install
```

Exit codes: `0` success, `1` Roblox/deployment failure, `2` configuration or usage error. An unexpected error prints a one-line message; `ROBOPS_DEBUG=1` shows the full Python traceback.

Publishing a place is never retried after a network error or a 5xx answer once the file may have reached Roblox (that would create a second version): the message then asks you to check the place's version history.

The API key is **never** passed as an argument (it would show up in logs): it is read from the variable named by `api_key_env`.

## Web dashboard

```powershell
$env:ROBLOX_API_KEY = "your-key"
$env:ROBOPS_GITHUB_TOKEN = "github_pat_..."   # optional, see below
robops dashboard
```

Run it from your game's folder (where `robops.toml` is): it opens a page in your browser, served by robops on your own PC (`http://127.0.0.1:8765`). Keep the terminal open; `Ctrl+C` stops it.

| View | What you see | What you can do |
|---|---|---|
| **Live game** | players online, visits, favorites, likes, each public server as a brick filled with its players, places and their last update, experience settings, last deployment | restart the servers, launch a deployment |
| **Charts** | players online, public servers, new visits, favorites and likes over time (6 h to 30 days); new players per day, players by last visit, sessions per player and the distribution of **every numeric field of the players' Data** (coins, level, inventory size…) from a backup; deployment runs per week and their duration; size of each backup | pick the period and the backup |
| **Deployments** | the latest runs of the *Roblox Deploy* workflow: target, status, branch and commit, author, duration (refreshed every 10 s while one is running) | launch a deployment (branch, version type, servers, DataStores) |
| **Players and backups** | search by UserId or username: avatar, online/offline, profile data; local backups and the nightly GitHub backups | edit a player's data in a code editor (changed fields shown before saving), restore them from a backup, delete their profile, run a backup now |
| **Simulated players** | the reports Claude saves after simulating players in Studio through the Roblox MCP (summary, problems found by severity, what each simulated player did and would say, measures), new ones appearing by themselves, whether Claude Desktop is connected, and when Claude used Studio | add robops to Claude Desktop, manual instructions, paste a report |
| **DataStores** | every DataStore of the experience, its keys (prefix, scope), each value with its revision and metadata | create, edit or delete a key, take a snapshot |
| **Setup** | the result of `robops check` for each environment, GitHub repository and token | — |

Every button opens a confirmation in the environment's colour (production in orange, staging in teal). For an environment whose name contains `prod` or `live`, you have to type its name; deleting a player also asks for the UserId. The player protections of the CLI apply: no write to an online player (unless you tick *force*), conditional write (etag), and a copy of the profile in `.robops/safety/` before any change. Every action is appended to `.robops/audit.log`.

**GitHub.** Deployments and GitHub backups come from the repository of the `origin` git remote (or `--github-repo owner/name`). For a private repository, set `ROBOPS_GITHUB_TOKEN` to a fine-grained token on that repository with **Actions: Read** (and **Read and write** for the *Deploy* and *Back up now* buttons). Without a token, these two parts only work for a public repository; the rest of the dashboard does not need GitHub.

**Security.** The server only answers on `127.0.0.1`, refuses any other `Host` (DNS rebinding) or foreign `Origin`, and every request must carry the random session key contained in the link printed at startup: another website open in your browser can neither read the data nor press a button. The page loads nothing from the internet except avatars (`rbxcdn.com`). Don't share the link while the dashboard runs.

**Editing data.** A player's data and DataStore values are edited in a JSON code editor:
- syntax colours, line numbers and the current line;
- indentation kept on Enter, `{` `[` `"` closed automatically, matching brackets highlighted;
- lines changed since loading marked in the margin, with a count in the status bar;
- errors pointed at their line and column with a plain explanation (missing comma, comma before `}`, unclosed text, `tru` instead of `true`…). Invalid JSON is never sent.

| Shortcut | Action |
|---|---|
| `Ctrl+S` | save (opens the usual confirmation) |
| `Shift+Alt+F` | format |
| `Tab` / `Shift+Tab` (or `Ctrl+]` / `Ctrl+[`) | indent / outdent the selected lines |
| `Ctrl+Z` / `Ctrl+Shift+Z` | undo / redo |

*Revert* goes back to the value loaded from Roblox.

**Simulated players (Claude + Roblox Studio MCP).** When Claude simulates players in Studio through the Roblox Studio MCP, its conclusions stay in the conversation. robops gives Claude its own MCP tool to save them in your project, where the *Simulated players* view shows them as soon as they arrive:

1. **Connect Claude** (once), from your game folder: click **Add robops to Claude Desktop** in the *Simulated players* view, or run `robops mcp install`. robops adds itself to Claude Desktop's `claude_desktop_config.json` (your other servers are kept, the previous file is copied to `claude_desktop_config.json.robops-backup`). On Windows it writes where Claude Desktop really reads it, including the Microsoft Store/MSIX install (`%LOCALAPPDATA%\Packages\Claude_…\LocalCache\Roaming\Claude`).
2. **Quit Claude Desktop completely** (tray icon → Quit) and open it again.
3. Roblox Studio's MCP server must be in Claude Desktop too: in Studio, *Assistant → … → Manage MCP Servers → Enable Studio as MCP server*, then *Quick connect → Claude Desktop*. The view and `robops mcp status` tell you if it is missing.
4. In Claude Desktop, pick **+ → robops → simulate_players** (the method to follow, with the number of players and what to test), or simply ask *"Simulate 5 new players doing the tutorial and save the report with robops"*. Claude calls `save_playtest_report` at the end: the report (format `robops-playtest/1`) is written to `.robops/playtests/` and appears in the dashboard by itself. Claude can also read earlier reports (`list_playtest_reports`, `get_playtest_report`) to check whether a problem is fixed.

```bash
robops mcp install      # add robops to Claude Desktop, for the project of robops.toml (--project to choose)
robops mcp status       # is robops / Roblox Studio's MCP set up in Claude Desktop? how many reports?
robops mcp uninstall
# Claude Code (it does not read Claude Desktop's config): the dashboard shows the exact line, e.g.
claude mcp add robops -- "C:\Users\me\AppData\Local\Programs\robops\robops.exe" mcp serve --project "C:\Games\MyGame"
```

Each report shows the summary, the problems found sorted by severity, each simulated player (profile, outcome, time, feedback, steps) and the measures. Without the robops tool (Claude elsewhere, another AI), **Manual instructions** gives a text to paste so that Claude saves its reports with Studio's `run_code` into the DataStore `RobopsPlaytests` of the universe (`[playtests] datastore = "…"` in `robops.toml`; needs *Enable Studio Access to API Services* in Studio, and `universe-datastores.objects` → *List* and *Read* on the API key), and **Paste a report** stores a report given as JSON. JSON files in a `playtests/` folder of the project are read too.

Below the reports, *Claude's actions in Studio* shows when Claude used Studio, from Claude Desktop's MCP log on this PC (`%APPDATA%\Claude\logs` or the MSIX folder on Windows, `~/Library/Logs/Claude` on macOS; `--claude-logs <folder>` otherwise). Recent Claude Desktop versions only log a summary of each call (time, success or error), so the tool name, its code and Studio's answer appear only with older versions that logged the whole message; what the players did is in the reports.

**Charts.** Roblox only gives *current* numbers, so the dashboard records the public stats (players, visits, favorites, votes, servers) every 5 minutes while it runs, in `.robops/stats/<environment>.jsonl` (`--sample-every 15` changes the pace, `0` turns it off; no API key needed). The line breaks where nothing was recorded rather than guessing. To keep a history while the dashboard is closed, schedule `robops stats record`, for example every 15 minutes with the Windows Task Scheduler:

```powershell
$action = New-ScheduledTaskAction -Execute "$env:LOCALAPPDATA\Programs\robops\robops.exe" -Argument "stats record" -WorkingDirectory "C:\path\to\your\game"
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 15)
Register-ScheduledTask -TaskName "robops stats" -Action $action -Trigger $trigger
```

The player-base charts are computed from a player backup in the `backups/` folder (the latest one of the environment's universe is picked; a nightly GitHub backup must be unzipped, and decrypted if it is `.age`). Every chart has a *Show as a table* view, and its values can be read with the mouse or with the arrow keys.

Options: `--port 9000`, `--no-browser`, `--github-repo owner/name`, `--deploy-workflow deploy.yml` / `--backup-workflow backup.yml` (by default the workflows created by `robops init` are found even if renamed). If deployments don't show up, the **Setup** view checks the GitHub connection step by step (token, access to the repository, Actions permission, workflows) and says what to fix. Live player counts come from roblox.com's public API; for a multi-place experience, Roblox only counts the players of the start place there.

## Player data (ProfileStore / DataService)

The `robops player …` commands understand the **ProfileStore** format, used by leifstout's DataService (and compatible with ProfileService). By default they target the `Default` DataStore with `PLAYER_<UserId>` keys, DataService's default values. If your `DataService:init` passes `profileStoreIndex` or `profileStoreDataPrefix`, copy them into the `[players]` section of `robops.toml` (or use `--datastore` / `--prefix`).

```bash
# View a player (Data on stdout, session state on stderr)
robops player get 123456 --env production
robops player get 123456 --env production --raw          # full profile

# Back up all players (.json.gz to compress)
robops player backup --out backups/players-2026-10-15.json.gz --env production

# Restore a player from a backup
robops player restore 123456 --from backups/players-2026-10-15.json.gz --env production --dry-run
robops player restore 123456 --from backups/players-2026-10-15.json.gz --env production

# Fix an offline player
robops player edit 123456 --set coins=500 --set stats.level=10 --env production
robops player edit 123456 --set 'inventory=["sword","shield"]' --unset tempFlag --env production

# Disaster: everyone goes back to the backup state
robops player restore --all --from backups/players-2026-10-15.json.gz --env production --dry-run
robops player restore --all --from backups/players-2026-10-15.json.gz --env production --yes
# (profiles deleted since the backup are skipped; --recreate-missing to recreate them)

# Data erasure request (right to be forgotten)
robops player delete 123456 --env production --yes
```

Built-in protections:

- **Player online = write refused.** The profile carries a lock (`MetaData.ActiveSession`) while a server owns it. That server saves every 5 minutes and would overwrite the change. To fix a connected player, use an admin command in the game.
- **Stale lock = removed.** If the last save is older than 630 s (ProfileStore's threshold), the server is considered crashed and the lock is removed on write.
- **Only `Data` is replaced.** `MetaData` (counters), `GlobalUpdates` (pending messages), `UserIds` and the entry's Roblox metadata are kept.
- **Conditional write (etag).** If the player joins between the read and the write, Roblox refuses the update and nothing is written.
- **Local safety copy.** Before every write or deletion, the old profile is copied to `.robops/safety/`.
- **`--all` requires `--yes`**, and online players are skipped (and listed) instead of blocking the whole restore.
- **No bulk resurrection.** With `--all`, a profile deleted since the backup (for instance after a data erasure request) is skipped, unless `--recreate-missing`. Never use that option if some players were deleted at their request.
- **Right universe.** A backup made by `robops player backup` remembers its universe: restoring a staging backup into production is refused unless `--allow-other-universe`.

If the backup finds no player while the DataStore contains keys, robops prints examples and the `key_prefix` value to put in `[players]`. The backup is written as it goes with 4 parallel reads (`--workers`, up to 16); the file only appears once complete. It also accepts exports made with `robops ds export`.

> ⚠️ Backups and safety copies contain players' **personal data**. `robops init` adds `.robops/` and `backups/` to `.gitignore`: never commit them, especially in a public repository.

If `useMock` is enabled in DataService (tests in Studio), that data is never written to a DataStore: there is nothing to back up.

### Automatic backup on GitHub

The `.github/workflows/roblox-backup.yml` workflow (created by `robops init`) backs up all profiles **every night** at 02:17 UTC, and on demand via *Actions → Player Backup → Run workflow*. It uses the same `ROBLOX_API_KEY` secret; the key must have, for `universe-datastores`, the permission to list keys and read entries.

Each backup is kept **30 days** as a run artifact: *Actions → Player Backup → click a run → Artifacts section → download*. Anyone with read access to the repository can download it, so **encrypt it** (recommended, it contains personal data):

1. On your PC, with [age](https://github.com/FiloSottile/age): `age-keygen -o robops-backup-key.txt`. Keep this file safe (password manager…), never in Git.
2. Copy the `age1…` public key it prints into a repository **variable** named `BACKUP_AGE_RECIPIENT` (*Settings → Secrets and variables → Actions → Variables*). The generated workflow passes it to the action's `age-recipient` input; only the encrypted `.json.gz.age` file is uploaded.
3. To read a backup: `age -d -i robops-backup-key.txt players-….json.gz.age > players-….json.gz`.

To restore, unzip the downloaded .zip (and decrypt it) then:

```bash
robops player restore 123456 --from players-production-2026-10-15_0217Z.json.gz --env production
```

Good to know: scheduled tasks only run from the default branch (`main`) and can be delayed when GitHub is busy; on failure, GitHub emails whoever last modified the `cron` line. In a **public** repository, GitHub disables them after 60 days without activity. Each backup uses about one minute of the GitHub Actions quota (2,000 min/month on the free plan for a private repository) and a bit of artifact storage (500 MB on the free plan): reduce `retention-days` if your game has many players.

## Rolling back

Re-run the workflow manually on the previous commit (or a tag), or republish the kept artifact:

```bash
robops publish place-production-<sha>/game.rbxl --env production
robops servers restart --env production
```

For data, every deployment with `--with-datastores` takes a snapshot first: previous values remain recoverable for 30 days through the revision history.

## Limitations to know about

- The publishing API **does not update** certain instance types: `EditableImage`, `EditableMesh`, `PartOperation` (unions), `SurfaceAppearance`, `BaseWrap`. If you change them, publish once from Studio.
- The metadata update fails (409) if a **Team Create** session is open on the place: this is a warning, not a failure (except with `--strict-metadata`).
- Publishing is limited to about **30 requests per minute** per key owner.
- Only one DataStores snapshot per UTC day; later ones have no effect.
- Overwriting a DataStore entry erases its `users` and `attributes` on Roblox's side: `robops` reads them back and sends them again automatically (can be disabled with `--clear-metadata`).

## Development

```bash
pip install -e ".[dev]"
pytest
ruff check src tests exe
mypy
```

The CI runs the tests on Linux (Python 3.11 to 3.13) and Windows, plus ruff and mypy. Notable changes go in `CHANGELOG.md`; short, descriptive commit messages (e.g. `fix: keep backslashes of the build command on Windows`) also make the release notes, which GitHub generates from them, readable.
